## 1. 总体方法：Fail-closed 三分类失败模型

仓库采用文档化、强制性的「安全 / 完整性 / 可用性」三分类失败语义（见 `docs/contracts/failure-model.md`），作为全仓错误处理的权威裁决。三类行为约束如下：
- Security：fail-closed，拒绝操作/连接/启动，禁止静默放行或降级。
- Integrity：degrade-safe，保留可验证子集、写 diagnostics、丢弃不可信块；调用方必须 `assert` 或表面化。
- Availability：recoverable，允许重试、abort-and-join、释放 lease、展示可恢复错误。

代码注释约定使用 `// failure-class: security|integrity|availability` 在边界函数处标注意图（第 119 行）。

## 2. Provider 层错误类型与流式协议错误

核心位于 `src/main/agent-runtime/providers/internal/http.ts`，定义一组专用 Error 子类：
- `ProviderHttpError`：真实 HTTP 4xx/5xx，携带 `status`、`providerApi`、脱敏后的 `bodyText`。
- `ProviderWireFailureError`：SSE `error` / `response.failed` 无明确 status 时的 wire 失败，携带 `wireCode`、`bodyText`。
- `ProviderEmptyStreamError`：流结束但无 assistant 正文或结构化 tool call，固定 `code = 'PROVIDER_STREAM_EMPTY'`。
- `ProviderTimeoutError`：分阶段超时（first-byte / idle / total）。
- `ProviderStreamBufferError`：流缓冲超过 8MiB fail-closed 截断。

通过 `createResponsesStreamFailure` 统一把 provider SDK 的 wire 错误映射为上述两类之一，并仅在存在显式 status 时合成 `ProviderHttpError`，禁止把空流冒充 HTTP 502。

共享类型 `src/shared/types/providerErrors.ts` 定义 `ProviderErrorCode` 联合（`auth_unconfigured`、`rate_limit`、`quota_exceeded`、`network`、`timeout`、`context_overflow`、`stream_protocol`、`aborted` 等）及 `AssistantMessageDiagnostic` 结构，用于跨进程诊断传递。

## 3. 错误恢复策略：`ErrorRecovery` 与 `AgentRecoveryAbortError`

`src/main/agent-runtime/agent/ErrorRecovery.ts` 提供纯逻辑的错误分类与恢复决策器：
- `classifyError` 将任意 Error 归入 `rate_limit` / `overloaded` / `prompt_too_long` / `max_tokens` / `auth_error` / `network_error` / `server_error` / `empty_stream` / `stream_protocol` / `unknown`。
- `decide` 按优先级返回 `retry` / `reactive_compact` / `switch_model` / `continue_prompt` / `abort` 动作，内置指数退避（base 1s + 0–500ms jitter）与连续过载阈值（3 次后切换 fallback model）。
- `AgentRecoveryAbortError` 是最终中止信号，强制通过 `createAbortError` 构造，始终携带 `cause` 链、`category`、`attempts`、`maxAttempts`、`lastStatus`、脱敏的 `bodySnippet`（≤300 字符）和可选 `streamCode`。
- `redactRecoverySnippet` 自动脱敏 Bearer token、api_key、access_token、secret 等敏感字段。

上层 `AgentLoop` 不得把 provider `error` 事件 remap 为 `message_end`；`error_recovery_*` 事件不进 Work Process，最终失败聚合为一条 diagnostic（含 `technicalMessage`）。

## 4. 领域内错误类型：按模块隔离的强类型错误码

每个业务域维护独立的错误常量数组与 `XxxError extends Error` 子类：
- `src/main/investigation/investigationErrors.ts`：`INVESTIGATION_SESSION_DENIED`、`INVESTIGATION_SCHEMA_INVALID`、`INVESTIGATION_INDEX_CORRUPT` 等，并提供 `toInvestigationError` 把 `ZodError` / `SessionArtifactError` 归一化为 `InvestigationError`，以及 `isInvestigationStoreDegraded` 判断降级态。
- `src/main/knowledge/knowledgeErrors.ts`：`KNOWLEDGE_HUMAN_CONFIRMATION_REQUIRED`、`KNOWLEDGE_CANDIDATE_REQUIRES_INTENT`、`KNOWLEDGE_REVISION_CONFLICT`、`KNOWLEDGE_WRITE_PATH_REJECTED`、`KNOWLEDGE_APPROVAL_TOKEN_INVALID` 等，全部带 `code` 只读属性。
- 其他模块（如 `conversation`、`settings`、`sessions`）也遵循相同模式：集中 `xxxErrors.ts` + 常量数组 + 自定义 Error 子类 + `toXxxError` 归一化函数。

## 5. IPC 与输入校验层的错误处理

IPC handler 层（`src/main/ipc/*Handlers.ts`）通过 `parseIpcArgs` + Zod schema 对入参做严格校验，非法 payload 直接抛错，避免下游消费脏数据。`runContextUsageBoundary` 封装 handler 执行，捕获异常并转换为统一的 IPC 响应错误格式。

## 6. 架构约定与约束

- 禁止裸 `new Error('[Recovery abort]')`：所有恢复中止必须经 `ErrorRecovery.createAbortError` 构造，保证 `cause` 链与结构化诊断字段完整。
- 禁止把可用性故障一律升级为安全 fail-closed，也不得把安全边界降级为“尽量继续”（failure-model 文档约束）。
- Provider 失败诊断保真：不得把空流冒充真实 5xx，不得把 Agent loop 停滞误报为 Provider failure；Turn 失败对外统一 code 为 `CONVERSATION_LLM_REQUEST_FAILED`，内部按 cause 分类生成 `userMessage` 与 `technicalMessage`。
- 存储损坏走 quarantine + `STORAGE_CORRUPT` / `STORAGE_SCHEMA_UNSUPPORTED`，未知更高 `schemaVersion` 不 quarantine。
- 单条 JSONL 损坏仅报告 diagnostics 并保留可读行，全文件不可读才抛文件级错误。
- 用户主动取消 turn 属于 Availability：abort-and-join 后允许下一 turn，不把 session 标为不可信。
