# RDC-Agent 垂直调查设计

## 文档定位

本文描述 Debug、Analysis、Optimize 三种垂直调查的目标架构：要达成什么、谁负责什么、信息怎样流动、什么算完成。它只写不随实现进度变化的内容。

- `ARCHITECTURE.md` 与 `docs/contracts/` 裁决产品边界和跨层合同；本文与之冲突时以它们为准，再回来修正本文。
- 实现状态、设备情况、已知缺陷和执行顺序不写在这里，分别见[收敛计划](../workflows/vertical-investigation-convergence.md)与[验收账本](acceptance-ledger.md)。
- 本文写了某项能力，不代表它已实现或已验证。

## 1. 目标与范围

### 1.1 目标

用户给一句症状或一个分析目标，Agent 能在当前 capture 上自主把问题查到证据允许的深度：定位对象，判断知识是否适用，组织竞争解释，选择有区分力的检查，处理反证，适时请独立核验，然后交付。换一个案例，它重新定位、重新建立解释，不套用上一个案例。

流程、知识与 Harness 都服务于泛化处理各自领域的问题。历史案例的答案不进入通用 Profile、Skill、Hook、工具分支或完成条件；几个历史案例通过不等于泛化完成。

### 1.2 三种 Mission

| Mission | 核心问题 | 交付内容 |
|---|---|---|
| Debug | 为什么出现异常？ | 触发条件、故障位置、传播机制、竞争解释、区分验证、适用范围和剩余未知 |
| Analysis | 渲染系统怎样工作，或者发生了什么变化？ | 执行与资源结构、关键计算、跨 capture 对应与差异、解释层次和不确定边界 |
| Optimize | 在质量和正确性约束下，哪些成本可以降低？ | 可信基线、限制因素、候选干预、实测收益、质量代价和恢复证据 |

三者共享知识、证据、上下文和生命周期基础，各有自己的方法与完成资格。Analysis 和 Optimize 按自身目标收敛，不是改了名的 Debug。

### 1.3 范围边界

调查与验证的边界是 capture、replay、已授权工具及相关只读材料。批准范围内可以做回放侧 Shader 替换、受控干预、测量和恢复。

- 不修改 Unity／Unreal 工程，不构建工程，不把 replay 结果称为生产修复已完成。可以分析已授权的源码并提出修复位置。
- 不修改原始 capture 字节，不把复制大型 capture 当作常规做法。
- 不自动扩大目标、设备范围、权限或输入集合。
- 不增加独立 Goal 模式、额外顶层 Mission 或第二套调查存储。
- 不为每个专业步骤或 Mission 与专长的组合新建 Agent 身份。
- 不恢复 Embedding、Semantic lane、自动 `agent_handoff` 或固定 workflow 阶段。

通用 General 仍可承担另行提出的普通编码任务；这里限定的是垂直 Mission 的范围。

## 2. 调查主线

每得到一个结果，都回到这条主线判断下一步。它是判断顺序，不是固定的工具序列。

1. **锚定**。把用户目标落到当前 capture 的具体对象：哪张原生纹理、哪个区域、哪个事件或 draw、哪条资源链，以及"它就是用户所指"的依据。依据分三档：用户确认；两条独立路径互相印证；仅候选。
2. **解释与预测**。对已锚定的对象保留互相可区分的解释。每条说明成立时应观察到什么、什么观察会削弱或排除它。
3. **区分检查**。在合法、可执行的检查里选最能改变判断的一项，说清它区分哪几条解释；结果回来后更新谁被支持、削弱、排除或暂缓。
4. **记录**。在决策点把锚点、解释、实验和未执行的检查写入调查记录。
5. **独立核验**。形成拟接受的主张后，由独立上下文核对来源、方法、覆盖和反例。
6. **继续或交付**。还有合法且有区分力的检查就继续；否则交付，并逐项说明未决内容。

**锚定是前提。** 锚点仍是"仅候选"时，首次异常、解释区分和因果实验都没有成立的基础；此时下一步优先选择能确立或否定锚点的检查。对象或区域确有歧义且现有材料无法判定时，问用户一次是正常做法：这是只有用户掌握的事实，不是让用户提供方法。

**顺序可以自适应。** 定位帮助判断知识是否适用，知识也帮助选择值得定位的对象；低成本的绑定或计算特征核对可以先做，用结果缩小范围。昂贵或受限的精确取证不是其他合法分析的共同前置。

**未知不是停止的理由。** 未证明最早异常，首次异常就保持未知；未完成合格实验，就不提升因果资格。这些表达结果边界，不自动成为停止获取该结果的理由。画面改善本身不证明根因；符合预测只增加支持。

## 3. 角色与循环

### 3.1 分工

| 概念 | 负责什么 | 不负责什么 |
|---|---|---|
| Planner | 澄清目标，决定范围、完成条件、候选方法和计划 | 未批准时执行高权限实验 |
| Orchestrator | 保留全局目标，分配工作，整合证据与审查，选择下一步 | 把局部产物自动升级成目标完成 |
| Generator | 获取材料、形成解释、执行合法实验、产出候选结果 | 以自己的叙事代替独立核验 |
| Verifier | 核对目标覆盖、来源、方法、反例和结论资格，给出具体缺口 | 改目标、扩大权限、把主观偏好升级为新验收标准 |
| Goal | 持续保留目标、完成条件、已完成部分和未决问题 | 充当额外模型或固定阶段控制器 |
| Runtime | 保证身份、权限、配置、消费、取消、引用和状态真实 | 用关键词规则判断科学结论真伪 |

Mission 承担规划和正式评估；General 承担获批计划的执行编排，也是唯一操作 live RDC 的身份。Generator 和 Verifier 是 General 组织的工作，不是新增的用户模式。普通任务仍由 General 按需完成，不强制进入完整调查流程。

### 3.2 Goal、Small Loop、Big Loop

- **Goal**：要达成什么，怎样知道达到，哪些边界不能越过。计划变化时目标可以不变；目标变化必须有明确依据。
- **Small Loop**：在批准的目标和战略内补证、区分解释、处理反例、改善测量和核验质量。
- **Big Loop**：当前战略不再成立，或继续需要改变范围时，保存缺口、重新规划并取得批准。

三者是不同维度，不是"Goal 调用 N 次 Small Loop，失败就自动 Big Loop"。调查方法由 Agent 根据证据决定；运行时只维护真实状态和授权边界。

### 3.3 交接边界

Mission 规划 → 用户批准并点击执行 → General 就地交付 → 用户按需要切回 Mission。Big Loop 由 General 交付 Checkpoint 和重规划理由，用户切回 Mission，再批准新计划。

持续目标不授权自动跨越这条边界。系统可以保持"目标未完成、等待计划决定"，但不暗中切换 Profile、不自动批准新计划、不重启用户停止的任务。

### 3.4 规划定位与执行定位

| 层次 | 要解决的问题 | 分工 |
|---|---|---|
| 问题与候选范围 | 哪个对象、哪种异常、哪些 Pass／资源／事件范围可能相关 | Planner 在只读能力内做有限探测；能确认的范围带证据交接 |
| 执行入口 | 已有材料是什么，先核对哪个对象，未知 ID 怎样取得 | Planner 交付可执行策略，不只列通用候选原因 |
| 精确对象归属 | 哪个 draw 真正绘制目标区域，用了哪些 shader、资源和绑定 | Generator 继承已确认范围后验证或细化 |
| 首次异常与机制 | 异常从哪个事件或计算开始，怎样传播 | Generator 取证并做区分实验，Verifier 核查 |

规划不能只写"之后定位 draw，再分析 shader"，也不必为了填出精确 ID 先完成整场调查。只读能力能安全取得的范围应先取得并带来源、精度和未知项交接；取不到时说明缺什么、哪项首批检查能取得它。

Planner 的探测能力是显式的只读闭集。某项操作理论上只读，不等于 Planner 已有这项权限；需要扩大时显式修改工具与权限合同，不靠提示词扩权。Generator 继承有效范围，因身份变化、证据不足或出现反证需要重验时说明理由。

## 4. 继续、完成与停止

### 4.1 四种完成

1. 工具调用成功：取得一个结果。
2. 局部 Task 完成：完成所分配的交付物。
3. 审查完成：核查了指定内容，可以留下仍然开放的问题。
4. 目标达到完成条件：必需覆盖完成，结论获得足够支持，并按交接合同交付。

四者不等价。完成一次实验不等于验证了根因；Verifier 完成审查并指出阻断项，不允许父任务把它当成已解决。

### 4.2 继续与收口

1. 得到关键结果、收到审查或准备结束时，Orchestrator 对照原目标更新已满足项和剩余项。
2. 剩余项分三类：当前可执行且有价值的下一步；需要外部条件的工作；需要重规划的工作。
3. 批准范围内有有效下一步时继续 Small Loop，不因已写报告、完成一轮实验或收到审查而结束。
4. 宣布完成时，使用绑定到当前成果版本的核验结果，检查必需覆盖和未决阻断项。
5. 交付 partial 时，逐项说明缺口、已尝试的路径、阻止继续的条件和恢复条件。没有真实阻塞的条目是应继续的工作，不是 partial 的理由。
6. Runtime 核验完成声明所依赖的可确定事实：必需 Task、审查执行、来源版本、回执和真实中断原因。无工具终答不能直接提升为目标完成。
7. 普通模型提前终答而必需合同未满足时，把具体缺口返回同一逻辑执行，沿用授权与消费。用户取消、真实额度或期限、安全失败、等待用户输入或 Big Loop 待批准时不自动续跑。

外部反复发送"继续"不是自主持续执行。已知设备事实的告知、计划门的批准、产品生成的交接属于正常输入；外部补充调查方法或催促续跑属于人工介入。

### 4.3 Verifier 如何影响下一步

核验结果表达：核查范围、读到的证据、已支持和未支持的部分、反例、资格限制、具体后续检查，以及是否影响必需完成条件。

Verifier 不拥有最终目标，也不能提高标准。Orchestrator 把有效缺口变成可执行工作；认为某项审查要求不适用时给出依据并保留可审计的处理。独立上下文和不同模型是两个维度：同一模型的独立执行可以满足隔离；严谨程度由材料覆盖和错误检出能力证明。

### 4.4 防止空转

| 情形 | 应有行为 |
|---|---|
| 相同调用、相同结果、相同现场 | 机械无进展检测生效，不无限重试 |
| 调用不同，但没有新增证据、解释区分或完成项变化 | Orchestrator 说明下一步为何仍有信息价值，否则收口 |
| 同一证据版本反复送审 | 复用已完成审查；新审查须有新增材料或范围变化 |
| Verifier 与 Generator 反复争论同一缺口 | 查清分歧需要什么证据；取不到时保留分歧 |
| 所有有效检查都依赖缺失的能力或材料 | 真实 blocked 或 partial，列出恢复条件 |
| 目标已满足，还想继续提高质量 | 非必需改进不阻止完成 |
| 只有记录格式或引用错误 | 修正记录，不重跑有效实验 |
| 有活跃子执行或设备操作 | 等待或取消并 join，不在后台仍在变更现场时宣告完成 |

是否有语义进展由模型判断；runtime 核验引用和状态变化，不把"新写了一条记录"当作进展。

### 4.5 限额

业务完成由目标、证据和审查决定，不由固定轮数决定。用户未配置总量限制时，不把内部默认请求次数当作交回的理由；Profile、policy 或用户明确设置的上限继续生效。

取消、显式预算、期限、权限、请求超时、资源所有权、进程失效和无进展检测始终有效。Capsule 的局部预算只能收紧，不能扩大根限制。续跑、压缩、恢复和重新委派都沿用累计消费与原期限，不通过新建回合或同义 Task 清零。

## 5. 信息流

记录的价值在于被读到并改变下一步。每类信息都有明确的写入方、读取方和它影响的决定；只写不读的记录是成本。

| 信息 | 写入方 | 读取方 | 影响的决定 |
|---|---|---|---|
| 目标、范围、完成条件 | Planner，经用户批准后冻结 | 每个执行回合；压缩后重读 | 是否越界；是否达到完成条件 |
| 锚点及其依据档位 | Planner（候选或用户确认）、Generator（收敛） | Generator、Verifier | 后续分析建立在哪个对象上；是否先解决锚定 |
| 竞争解释及预测 | Generator | Orchestrator、Verifier | 下一项检查区分什么 |
| 未执行的有效检查 | Orchestrator，写入 Checkpoint | 续跑与复评、压缩、Big Loop 重规划 | partial 之后还能做什么；重规划从哪里接续 |
| Challenge 及其后续要求 | Verifier | Orchestrator；完成准入 | 需要补什么证据；能否宣布完成 |
| 未决项（缺口、已尝试、阻塞、恢复条件） | Orchestrator，随交付声明 | 用户；续跑准入 | 这是合理 partial 还是应继续的工作 |
| 证据与实验回执 | Generator；主进程签发回执 | Verifier；报告 | 结论资格 |
| 知识的适用条件 | 知识卡原文 | Planner、Generator | 历史机制是否适用于当前对象 |
| 现场与恢复回执 | 主进程 | 完成准入；用户 | 能否宣布完成；当前打开的是什么 |

独立审查只能读到被授予的内容，所以审查所需的原始证据须随被审主张一并授予。压缩和委派保留的是这些信息本身，而不只是它们的索引。

## 6. Agent、Skill 与模型配置

### 6.1 身份

四个用户入口：General、Debugger、Analyzer、Optimizer。八个内部 Agent：

| Agent | 职责 |
|---|---|
| `generator` | 综合证据、形成竞争解释、设计检查和候选实验 |
| `verifier` | 独立核验来源、方法、覆盖、反例与结论资格 |
| `knowledge-scout` | 多来源检索、适用条件比较、机制与检查建议 |
| `report-writer` | 根据有效成果组织报告，保留限制和未知项 |
| `shader-analyst` | Shader／IR、数据流、数值计算和语义重建 |
| `pass-analyst` | Pass、执行关系与管线结构重建 |
| `resource-analyst` | 资源版本、依赖和跨 capture 对应 |
| `pixel-analyst` | 图像、区域、片元材料与质量差异分析 |

内部 Agent 按任务需要调用，不要求每次全部参与。专业子执行只读取获授权材料、写自己的成果，不共享 live lease；Verifier 不修改父级记录，Report Writer 不重新评级证据。

### 6.2 模型配置

- 模型与推理档位归各 Agent 配置，在本机设置里管理；初始选择写入用户配置，不硬编码在分发资源。
- Composer 的覆盖只影响当前用户回合。子执行读取目标 Agent 的配置，不继承父对话覆盖；Capsule 只选择目标 Profile，不带模型或档位参数。
- 配置缺失、模型不可用或档位不支持时明确失败，不替换 Provider、不降档、不回退到父模型。
- 执行前、实际请求和完成回执使用同一冻结事实，可追溯 Profile、Skill、配置来源、模型、推理控制和被审成果版本。
- 同步与后台子执行共用同一路由与准入。设置变更只影响后续准备，不改写在途请求。
- 已批准的必需核验不能被父 Agent 自审、换 Profile、删除要求或另建普通 Task 绕过。成果版本失效时只重做受影响的部分。

### 6.3 承载分工

| 承载 | 放什么 | 不放什么 |
|---|---|---|
| `.agent.md` | 稳定身份、职责范围、工具与权限天花板、允许委派、默认 Skill、完成合同 | 案例解法、冗长工具手册、运行中进度 |
| Skill | 怎样从症状形成可检验问题，怎样定位、分析、实验、审查和解释结果 | 用户模型配置；不可绕过的权限与身份校验 |
| Task 执行要求 | 所需方法、独立性、目标 Profile、输出与版本依赖 | 自由文本扩权；父 Agent 临时改写模型或消费上限 |
| Hook | 在明确生命周期点执行已受信的检查、提醒或审计 | 自建循环引擎、自动批准 Big Loop、隐式扩权 |
| Knowledge | 可复用的事实、机制、案例、方法、反例及适用域 | 当前 Task 的执行状态；把历史结论强加给新 capture |
| Plan／Task／Investigation／Checkpoint | 当前目标、已知范围、首批检查、证据、未决方向和续跑状态 | 第二套模型路由；无来源的完成标记 |

Skill 提供方法，不授予权限，也不把按需读取变成新的预载门槛。关闭 Hook、修改 Skill 或自定义 Profile 之后仍须成立的权限、身份、消费和来源约束，放在权威服务与执行边界，由代码强制；方法文本不重复这些约束。

## 7. 知识

### 7.1 组织

Markdown 原文是唯一来源；索引和简介是可重建的派生物。不恢复 Embedding。

| 维度 | 表达的问题 |
|---|---|
| Fact／Constraint／Pattern／Procedure／Case／Model | 知识以什么形式表达 |
| 主题 | 讲什么领域内容 |
| 症状 | 外部观察到什么 |
| 机制或结构 | 为什么发生或怎样组成 |
| 任务用途 | 能帮助哪项决策 |
| Scope | 在哪些项目、版本、API、GPU、驱动、Pass 和质量条件下成立 |
| 来源与验证状态 | 有哪些证据、反例及资格限制 |

一份原文可以跨 Mission 使用，不复制成三份。主题采用少量统一的受控词表，允许同义词和多主题；新增、合并或同义映射由 Agent 提议、用户批量确认。未归类的材料仍可检索。Candidate 审核与主题确认是不同操作。

### 7.2 检索

六条通道各有职责：Identity／Path 精确定位；Scope／Metadata 匹配或过滤条件；Lexical 用词项发现材料；Structural 按章节结构定位；Relation／Graph 沿有来源的关联探索；Temporal／Version 查看时间与版本条件下的材料。

- 有文本查询时不靠无关的基础分制造命中；无条件浏览与文本检索分开。
- 关系冲突必须来自真实、可追溯的关系；共同关联第三张卡不构成冲突。
- 查询暴露 Scope、时间条件、分页和版本；截断、预览与后续读取保持同一内容版本。
- 命中直接呈现卡片声明的适用与排除条件；未声明的条件是未知，不是匹配。
- 读取支持简介、章节、范围和全文，返回版本、实际读取范围及图片引用。图片须实际读图才算观察到。
- 零命中不是失败：换知识类型继续找，或依据领域知识和当前观察提出可检验解释。工具失败与零命中分别报告。

### 7.3 知识怎样改变决策

读到的知识须完成三步转换：

- **对应对象**：它描述哪条计算或关系，当前要寻找什么特征，哪些条件已匹配、未知或不符。
- **形成预测**：若适用，应观察到什么；哪些结果会排除或削弱它。
- **确定行动**：下一项合法且有信息价值的检查是什么，所需 ID 和材料怎样取得。

历史卡处于 draft，说明不能继承它的验证资格，不说明它没有提供检查方法的价值。条件未知先核对，已证伪才排除。历史的 Event ID、ResourceId 或 Shader ID 不能套到当前 capture。

检索次数不固定：计划前可从症状和对象检索，执行中发现新计算或异常值后可再次检索；材料足以选择下一项检查，或继续检索的价值低于直接取证时停止。简单查询直接完成，复杂的多来源比较可委派 Knowledge Scout，由它返回来源、匹配理由、限制和可用的检查方法。

需要防止的通用错误：

- 症状相同就继承历史原因。
- 认出同一算法家族，就当作核对了历史材料中的具体计算。
- 干预后画面改善，就认为原机制已证明。
- 以"缺动态证据"为由，禁止取得该证据所必需的检查。
- 一个方向取得结果后，遗失尚未排除的替代解释。
- 只统计读了多少知识、调了多少工具，不看材料有没有改变决策。

## 8. 三种 Mission 的方法与完成资格

### 8.1 Debug

从现象和可观察证据开始，锚定对象，定位首次可确认的异常，建立竞争解释，追踪触发条件、故障计算或资源与传播路径，选择能区分候选的检查。反事实干预要分清修正故障、绕过故障与补偿结果。修复建议可以引用相关源码，但不修改外部工程，也不宣称生产修复完成。

### 8.2 Analysis

覆盖单 capture 的执行、Pass、资源依赖与组织结构；缺源码或标记时用事件、附件、顶点布局和 Shader IR 重建关键计算；跨 capture 比较资源、Shader、绑定、执行路径与画面差异。

Observed、Reconstructed、Authoring Hypothesis 表示结论依据，不是每个任务都要填满的三个章节。分析深度由用户问题决定，不要求先还原整个引擎，也不为完成而编造作者意图。资源增长不能仅凭两帧证明持续泄漏；无法对齐的对象保留未匹配与依据。

### 8.3 Optimize

先定义测量对象、质量约束和可信基线，再提出限制因素、选择干预、复测、恢复并检查质量。静态指令数、吞吐推测、局部 shader 耗时和端到端 GPU 时间分别说明，互不替代。单 capture 的实验结果不外推为跨设备、跨场景的收益。

### 8.4 完成、partial 与阻塞

| | 完成 | 合理 partial | 阻塞 |
|---|---|---|---|
| Debug | 锚点达到用户确认或互相印证；首次异常有证据；至少一个竞争解释被区分性观察削弱或排除；因果主张有合格的可恢复实验；当前版本经独立核验且无相关开放质疑 | 锚点已立，区分或因果所需能力不可用，逐项列出 | 锚点无法建立且用户未提供；设备、权限或输入缺失 |
| Analysis | 批准的每个分析目标都有对应成果；每条结论标明依据层次 | 部分目标已覆盖，其余列出缺口 | 输入不可回放；跨 capture 无法建立对应 |
| Optimize | 基线含样本数与离散度；收益超过实测噪声；有质量对照和恢复证据 | 有候选与局部测量，端到端测量不可得 | 没有任何可用的计时能力 |

预算耗尽不是完成；审查不可用不是通过；设备不支持不是已呈现。

## 9. 多 capture

一个任务可以接收多个已登记的 capture，用户一次说明比较目标，Agent 通过受控工具顺序取证并比较。界面继续展示当前活动 capture，但身份和进度必须真实。

1. 计划记录参与的 capture 集合、目标、设备和取证范围。新增未批准的输入或换设备按相应授权处理。
2. 每份材料绑定 capture 内容身份、取证身份和适用条件。Event ID／ResourceId 只在所属 capture 内有意义。
3. 同一 owning session 串行操作获批 capture。切换前结束相关子执行，关闭实验，恢复替换。
4. 切换经应用的受控生命周期进行；模型不直接改底层全局 context，不借用其他 session 的 lease，不指定任意路径，不默默改为 Local。
5. capture 或 lease 改变后重新准备；逻辑任务、调查进度和消费账本继续。
6. 取证完成后可以离线并行比较已授权的成果，不共享 live lease。
7. 跨 capture 对应依据执行位置、资源结构、计算特征和用途建立，并记录依据与歧义；不靠同名或同 ID。
8. 结束时恢复可恢复的入口现场，并说明当前打开的是什么。恢复失败时如实显示，不提示成功。

## 10. 上下文连续性

目标、Task、工作状态、按需知识和原始证据是内容的组织层次，不是多套存储。

**委派**须说明当前问题、所需判断、必要事实与证据资格、具体机制、竞争解释、反例和否定路径的适用条件、输入引用、必需方法、真实限制和交付要求。对子任务隐藏无关历史，不隐藏完成工作必需的机制依据。父任务保留全局目标并负责整合，"已委派"不等于"已处理"。

**压缩、续跑、恢复和重新委派之后**须能找回：

- 原目标、排除项、完成条件和批准计划。
- 当前候选解释及其机制和适用条件。
- 已完成工作和原始来源。
- 已排除方向、反证和重查条件。
- 尚未执行的有效检查及优先理由。
- 当前实验、设备和恢复状态。
- 真实停止限制、配置绑定、成果版本、累计消费与原期限。

不把未知压缩成否定，不把暂缓变成永久排除，不把局部完成写成目标完成，不对已失真的摘要反复压缩而不回到源证据。全文落盘、hash 正确、调用过读取，都不能单独证明模型理解并持续使用了材料。

## 11. 回放故障与续跑

### 11.1 自主恢复的范围

同一已登记 capture、同一已批准设备、原目标和权限范围内，Agent 可以请求受控恢复，重新准备后继续调查。换设备、扩大权限、改变目标或需要新的外部条件时找用户。用户主动停止的任务不自动重启。

### 11.2 责任

| 责任方 | 责任 |
|---|---|
| 主进程 | 分类失败、隔离、取消并 join 自有执行、关闭 context 与 daemon、取得进程回执、重开、核验身份 |
| Orchestrator | 读取状态与进度，判断材料可用性、必要重验和下一检查 |
| Verifier | 评估受影响的成果和依赖，不凭重开成功补认旧实验完整 |
| 用户 | 决定新的设备、权限、目标和战略；提供不可获取的外部输入 |

归属 daemon 先释放 context 再停止，以进程回执为准。不通过通用接口写回旧 ID，不在恢复中改用 Local 代替原设备。同一失败条件重复出现时停止无效重开。

### 11.3 证据恢复

| 内容 | 处理 |
|---|---|
| 有来源的截图、IR、资源表、完整实验 | 条件仍成立时继续作为历史事实使用 |
| 当前事件、连接、替换、能力和测量条件 | 在新现场重新核验 |
| 未返回可靠结果的步骤 | 保持未知，按需补做 |
| 中断实验的已保存阶段 | 保留为历史事实，不与新现场拼成一次完整实验 |
| 重开后仍要验证的原假设 | 在新现场建立基线并完成新的可核验实验链 |
| 已完成的 Task | 保留完成历史；补证使用正确的依赖和执行实例 |

相同的 capture 内容只说明文件相同，不说明设备、事件、替换、驱动或性能条件相同。

### 11.4 故障不等于战略失败

一次查询失败、现场被隔离、原战略已无可行取证路径，是三件事。前两者不自动证明第三者。现场被隔离后停止依赖 live replay 的操作，检查已保存的材料是否仍足以推进有价值的离线工作；不足时诚实等待恢复。同 capture、同设备的恢复不改变批准的目标与战略，恢复后继续原计划，不要求用户重新描述症状或重新规划。

语义早停与现场阻塞分别诊断：不因目标未完成就认定所有停止都错，也不用发生过故障来掩盖故障前没有把知识转成有效行动。

## 12. 交付与用户体验

- **进度**：Progress 显示目标相关的工作与真实状态；Artifacts／Outputs 引用真实成果；Context 显示与当前执行有关的材料和限制；Capture 显示真实的活动身份。不新增独立 Goal 开关，不展示隐藏推理链。
- **交付**：回答了什么、证据是什么、验证覆盖、仍未知什么、哪些结果只说明局部效果、现场是否恢复、是否需要用户决定。保留 completed、partial、blocked、cancelled 和预算中断的区别。
- **报告**：正式报告与 General 的执行交付职责分离。报告只消费具有相应资格的成果，写作阶段不把建议升级为结论。
- **审查频率**：必需核验按计划执行。额外复核放在影响主导解释、完成声明或无阻塞却准备结束的节点，不是每次工具调用。同一来源版本不重复审查；审查者的局部额度不足只说明该审查的限制。

## 13. 泛化与验收原则

### 13.1 不学固定答案

历史案例是有适用条件的知识材料和回归输入。通用方法不含案例专用参数、固定原因、固定实验顺序或答案匹配条件。知识库提供可检验的解释和方法，不替 Agent 宣布当前原因。

有对应历史案例卡的 capture 上取得的结果属于知识迁移，不是陌生问题泛化。未参与规则调整的保留材料，其真值不进入运行 Prompt 或通用知识。合成材料可以验证机制和边界，不冒充陌生真实工程的成功率；仅重命名对象不构成新的问题家族。

### 13.2 输入类型

| 输入类型 | 新增内容 | 怎样解释结果差异 |
|---|---|---|
| 症状级请求 | 对象、异常表现、调查目标 | 正常的自主调查入口 |
| 事实补充 | 目标区域、正常参考、已确认事件、独立实验结果 | 信息条件变了，单列，不算方法提示的收益 |
| 方法提示 | 一般调查步骤，不含新事实 | 表现明显改善说明方法自主组织存在缺口 |
| 原因或答案提示 | 根因、修复代码或预期参数 | 只检验执行与验证能力，不证明自主诊断 |

短症状是正常入口，用户不需要提供 Event ID、Shader ID、工具顺序或根因提示。

### 13.3 结果分类

自主完成、事实补充后完成、经方法提示完成、合理未完成、过早停止、错误结论、无效长跑。它们分别统计，不合并成一个通过率。

区分"工具不可用"与"Agent 没有选择有效检查"的办法是事后重放：对未执行的检查经同一产品路径亲自执行一次。评估重点是知识有没有改变下一步、实验是否区分了解释、反证是否被处理、原目标是否保留、核验是否读到当前版本的原始证据、停止是否有依据、恢复后现场身份是否实际得到核验。

### 13.4 验收层次

| 层次 | 完成标准 |
|---|---|
| 合同与确定性实现 | 正负路径、身份、路由、来源、状态和消费一致 |
| 方法与上下文 | 实际输入和关键决策可追溯，压缩与委派未改变资格 |
| 真实模型行为 | 不靠答案硬编码，正确使用材料并合理继续或停止 |
| 真实回放设备 | 实验、质量、恢复和设备效果有实际回执 |
| 泛化 | 未参与规则调整的真实材料上取得可复查结果 |

没有对应证据的层级保持未验证。构建通过、schema 合法、报告就绪或 mock 成功，都不能替代真实运行。对照须固定实际模型请求、知识版本、权限、输入和干净现场，并记录人工介入、耗时、token 与可得费用；条件未固定时不称严格对照。

## 14. 责任分层

| 层 | 负责 | 不承担 |
|---|---|---|
| 通用 Harness 内核 | 执行准备、授权、所有权、取消、消费、隔离委派、合同准入、真实终态与续跑 | 不认识头发、shader 或首次异常；不按 Mission 写固定调查顺序 |
| 可复用平台服务 | Knowledge 查询／读取／编译、Artifact、模型目录与路由配置、PromptPlan、Hook 执行基础设施 | 服务存在不等于每个任务必须使用 |
| 领域确定性合同 | RDC capture／replay／设备生命周期、身份和回执；Investigation 的记录、资格与报告约束 | 不靠提示词替代校验；不把领域字段加入通用 TaskStore 或 AgentLoop |
| 垂直方法组合 | `.agent.md`、Skill、声明配置、Hook 与知识共同组织规划、生成、核验和两种 Loop | 不自行授予工具、修改冻结配置、伪造证据或绕过生命周期 |

Renderer／preload 是这些事实的操作与投影边界，不新增另一套调度或领域真值。

审查实现时的边界检查：

- 通用文件里出现 Mission 身份分支、具体算法或症状、固定工具顺序，说明领域方法被放进了内核。
- Skill 或 Hook 写着"保证模型一定如此、保证恢复成功"，却没有权威服务检查，说明用文字代替了 runtime。
- 新能力只服务一个具体步骤，而现有 Task、准备或成果机制已能表达，应复用。
- 只有权限、完整性和已声明的必需执行要求由 runtime 强制；调查顺序与科学判断保持可调整。
- 同一事实的校验实现保持单一权威，不复制多份。

## 15. 已定裁决

**A. 执行职责的承载。** 保留四个用户入口，设八个内部 Agent。每个 Agent 通过现有设置配置模型和推理；Task 与 runtime 冻结并核验目标 Profile、方法、独立性与成果版本。Verifier 的执行义务不能被父模型临时覆盖。内部 Agent 的初始模型选择写入用户配置。

**B. 请求上限与持续执行。** 垂直调查不以固定默认总轮数收口，由目标与核验闭环决定继续和完成；用户显式限制及技术安全边界保留。执行分段、恢复和重新委派保存逻辑目标、消费和授权，不绕过真实上限。

其余已定事项：

- 合同是 Mission 规划 → 用户批准 → General 执行并就地交付。Big Loop 经 Mission 重新对齐和批准，不自动回切。
- 不新增第二套 Goal、模型路由、调查存储或固定工作流。
- 调查范围止于 capture、replay、授权材料及可恢复实验，不自动修改外部工程或原始 capture。
- 多 capture 通过同一 owning session 串行切换实现，结束时恢复可恢复的入口现场。
- 同 capture、同设备的受控恢复可自主请求；换设备、权限或目标找用户。
- Knowledge 的 Markdown 原文是唯一来源，不恢复 Embedding；主题由 Agent 提议、用户批量确认。
- Skill 提供方法，不授予权限，不把按需读取变成预载门槛。
