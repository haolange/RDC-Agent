# RDC-Agent 垂直调查能力完整收敛计划

## 1. 目标与已确定的架构决策

以《RDC-Agent 垂直调查能力收敛设计》为需求真源，并采用本次讨论确定的修订：**独立 Agent 承担稳定职责，默认装载匹配 Skill；所有模型与推理档位统一归属于 Agent 配置。**

目标是完整打通：

> 症状或分析目标 → 有依据的规划 → 用户批准 → 执行与专业委派 → 证据和竞争解释 → 独立核验 → 补证、恢复或交付。

当前核查基线为 `36306dbd3d5ca1f6663bcedda43ba6e25a0d0ba4`，工作树干净。本计划覆盖代码、用户配置、文档、UI、实际模型与 Android 验收，不以新增几个 Profile 或修复两项知识查询问题作为完成点。

确定以下边界：

- 保留 General、Debugger、Analyzer、Optimizer 四个默认用户入口，新增八个默认内部 Agent。
- General 负责获批调查的整体编排、结果整合和 live RDC 操作；专业 Agent 默认作为同级子执行，处理获授权材料，不共享 live lease。
- 持续执行以目标和证据闭合为依据，取消、显式限制、真实阻塞和等待批准仍然有效。
- 保留 Mission → 用户批准 → General 就地交付的交接方式；战略改变由用户切回 Mission，不自动切换或批准。
- 不增加第二套 Goal 存储、模型路由、调查存储或固定 workflow 引擎。
- 调查范围止于 capture、replay、授权材料及可恢复实验，不自动修改 Unity／Unreal 工程。

## 2. 实现变化

### 2.1 Agent 与模型配置统一

新增以下 `.agent.md`，均默认 `user-invocable: false`，通过现有 Agents 设置管理。

| Agent ID | 职责 | 默认装载的主要 Skill |
|---|---|---|
| `generator` | 综合证据、形成竞争解释、设计检查和候选实验 | `renderdoc-investigation`、`artifact-provenance`；按任务补充对应 Mission 方法 |
| `verifier` | 独立核验来源、方法、覆盖、反例与结论资格 | `skeptic-review`、`artifact-provenance` |
| `knowledge-scout` | 多来源检索、适用条件比较、机制与检查建议 | `knowledge-scout` |
| `report-writer` | 根据有效成果组织报告，保留限制和未知项 | `report-composition`、`artifact-provenance` |
| `shader-analyst` | Shader／IR、数据流、数值计算和语义重建 | `shader-ir-analysis` |
| `pass-analyst` | Pass、执行关系与管线结构重建 | `pass-graph-analysis` |
| `resource-analyst` | 资源版本、依赖和跨 capture 对应 | `resource-versioning`、`cross-capture-alignment` |
| `pixel-analyst` | 图像、区域、片元材料与质量差异分析 | `pixel-forensics` |

具体落实：

- 区分“内置 Agent 集合”和“默认顶层入口集合”，修正目前将二者等同的加载、校验、设置和测试。
- Profile 保持简短，只声明身份、职责、工具边界、允许委派和默认 Skill；专业方法留在 Skill，不复制多份提示词。
- General 根据任务委派上述 Agent；Mission 可委派 Scout 做复杂检索。默认不要求子 Agent 再次委派，不提高现有默认委派深度。
- 简单查询和普通 General 工作仍可直接完成；不强制每次调查调用全部八个 Agent。
- 专业子执行只能读取获授权材料、写自己的成果；Verifier 不修改父级记录，Report Writer 不重新评级证据。
- 保留历史非法 ID 的拒绝规则，不因增加新 Agent 自动激活旧 S0 配置。

**模型只有一个配置来源：**

- `.agent.md` 保留现有模型配置，新增可选 `reasoning-level`，解析为共享类型中的推理选择；Settings → Agents 复用现有模型与推理控件。
- Composer 覆盖仅影响当前用户回合。子执行读取目标 Agent 配置，不继承父对话覆盖。
- 从可执行 Capsule 接口删除自由 `model`、`reasoningLevel` 参数；委派选择目标 `profile`，不另选模型。
- 新增八个 Agent 的本机初始配置统一为 `chatgpt-account / gpt-6.1-sol / high`；通过现有配置保存链写入 User space，不硬编码到分发资源，不覆盖原有四个 Agent。
- 配置缺失、模型不可用或档位不支持时明确失败；不替换 Provider、降低档位或回退到父模型。

### 2.2 把 Agent 配置变成实际执行约束

沿现有 Task → Capsule → Prepare → RequestPlan → 执行回执补齐：

- `TaskExecutionRequirements` 增加目标 `profileId` 约束，继续复用必需 Skill、独立执行和来源 Task 依赖。
- 执行准备记录实际 Profile 来源与 hash、Skill hash、Provider／模型、推理控制、runtime fingerprint，以及被审成果的版本。
- 同步与后台子执行共用准入和解析逻辑；目标 Profile 不符、必需 Skill 未装载、来源版本过期或独立性不成立时拒绝结算。
- 已批准的必需核验不能被父 Agent 自审、换 Profile、删除要求或另建普通 Task 绕过。
- 设置变更只影响后续准备。在途请求继续使用冻结配置；新版本成果只使相关核验失效，不重跑无关检查。
- 默认 Skill 表示实际方法装载，不等于授权。工具权限仍由现有 Profile、policy、输入授权和能力交集决定。

### 2.3 持续目标、完成判断与停止行为

复用冻结计划、Task、Investigation、Checkpoint 和现有消费账本，补齐同一逻辑执行中的持续推进。

- 计划冻结目标、完成条件、必要任务、核验依赖和边界；Checkpoint 保存已完成项、未决检查、现场状态及停止原因。
- 明确区分工具完成、子任务完成、审查完成和目标完成。审查返回 open Challenge 时，审查任务可以完成，调查目标仍需处理其影响。
- 普通模型提前终答而必需合同未满足时，将具体缺口返回同一逻辑执行继续处理；不创建伪造用户消息，也不依赖 Stop Hook 循环发送“继续”。
- 最终交付前检查必需执行、当前版本核验、未决阻断项、活动子执行和实验恢复事实；科学结论由领域方法与核验判断，通用内核不解析症状或规定工具顺序。
- 保留 `completed / partial / blocked / cancelled / budget_paused` 的区别。部分交付必须说明未满足项、剩余检查及不能继续的具体原因。
- 移除内置默认总轮数和强制子任务小配额造成的正常早停；未配置总量限制表示未配置。Profile、policy 或用户明确设置的限制继续执行。
- Capsule 的局部预算改为可选的收紧约束，不得扩大根限制。续跑、重新委派、压缩和恢复都沿用累计消费与期限。
- 继续复用机械重复检测；语义空转由 Orchestrator 对照新增证据、解释区分和目标覆盖判断。不得靠新建同义任务刷新预算。
- 用户停止、硬限制命中、等待输入或 Big Loop 批准时禁止自动续跑；应用重启后由用户触发恢复。

### 2.4 Knowledge 的准确性、可读性与主题治理

首先修复文档已复现的确定性问题：

- 文本无匹配时不能靠 Identity、Scope、Temporal 的无条件基础分产生相关命中。
- 两张卡共同关联第三张卡，不得被编译成彼此冲突；冲突必须来源于真实、可追溯的关系。
- 词项查询支持归一化、词序变化和中英文文本处理，保留精确词组的区分价值；同义映射来自可维护词表，不恢复 Embedding。

补齐服务到工具及界面的完整链路：

- `knowledge_search` 接通 Scope、时间条件、分页、截断状态和同版本 preview；区分文本检索与无条件浏览。
- `knowledge_read` 支持简介、章节、范围和全文读取，返回原文版本、实际读取范围及图片引用。
- 搜索分页绑定索引版本；原文或索引变化时明确要求刷新，不混合不同版本的结果。
- lane reason 反映各自真实贡献；编译包身份包含内容版本与相关查询条件，不能仅靠卡片 ID 序列。
- 图片必须实际进入读图链路，文本引用图片不算已观察。
- 主题、知识类型、症状、机制、用途和 Scope 分开；未知主题材料仍然可检索。
- 在现有 Knowledge 管理流程增加主题及同义词的批量提议、预览和确认。可分析现有 User space 知识提出建议，但未经用户确认不改写正式分类，也不自动创建 Candidate 或晋升知识。
- Markdown 原文保持唯一来源；索引和简介是可重建派生物，不维护第二份知识正文。

### 2.5 三种 Mission 方法与上下文连续性

**共同要求：**短症状 Prompt 是正常入口，Agent 自己组织定位、读取和区分检查，不要求用户补写方法。

- Planner 在安全只读范围内确定对象、已有锚点和候选范围，交接来源、精度、未知项及首批检查。无法取得精确 ID 时说明获取路径，不伪造定位成果。
- Generator 继承有效范围继续细化，不能无依据从整帧重查；First Bad Event 的执行取证仍属于执行阶段。
- 知识必须转化为“当前对象如何对应、成立与不成立分别预测什么、下一项检查是什么”。允许知识检索与对象定位交错推进，不机械要求 Pixel History 全部完成后才能分析 Shader。
- Debug 保留故障位置、机制、竞争解释和合格区分实验的结论资格；画面改善不能单独证明根因。
- Analysis 按用户目标选择结构重建或跨 capture 比较深度。调整现有强制三层齐全的完成检查，禁止为通过门禁编造 Authoring Hypothesis。
- Optimize 分开静态推测、局部耗时与端到端收益，要求可信基线、噪声判断、质量检查和恢复证据；能力不足只能交付候选及限制。
- Capsule 和压缩继续使用原始引用与现有归档能力，保留竞争解释、反证、重查条件和未执行检查；不得将未知变成否定、暂缓变成排除。
- Verifier 读取必要源材料与约束，使用独立上下文；General 整合有效 Challenge、安排补证和更新父级记录。
- Report Writer 只组织已有成果，不将建议升级为结论，不承担隐藏的最终裁决。

### 2.6 多 capture、Android 与受控恢复

采用**同一 owning session 串行切换 capture**，复用现有产品生命周期。

- 计划明确批准的输入集合、设备及比较目标。General 通过受控工具选择已登记输入，不直接修改底层全局 context。
- 扩展现有 `rdc_probe` 生命周期能力，使其消费已批准设备，去掉固定 Local 的选择；按冻结权限向 General 暴露所需操作。
- 切换前结束相关子执行并关闭实验、恢复替换；捕获旧现场的必要回执后才能释放资源。
- capture 或 lease 改变后停止使用旧准备事实，重新 Prepare，再继续同一调查目标及消费账本。
- 每份证据绑定 capture、设备、现场和内容身份；跨 capture 对应依据结构、计算和用途，不靠相同 ID。
- 任务正常结束时恢复进入任务前的活动 capture，并核验可恢复的现场位置；无法恢复时明确显示当前状态，不能提示成功。
- 同 capture、同设备、同权限的故障允许请求自主恢复：隔离旧现场 → 取消并 join 自有执行 → 释放 context → stop 归属 daemon 并取得进程回执 → 重开 → 核验身份 → 重新准备。
- 同一失败条件重复出现时停止无效重开；设备、权限、输入或战略变化交给用户决定。
- 保留有效历史图像、IR 和已完成实验；新现场重新核验当前绑定、替换和测量条件。中断实验不得与新现场结果拼成一次完整旧实验。
- 现场失效时继续有价值的离线分析；恢复本身不自动触发 Big Loop。

### 2.7 UI、文档与数据转换

UI 沿现有页面和 Session rail 补齐：

- Agents 设置展示内部 Agent、默认 Skill、模型、推理档位及配置错误，不新增“子任务模型”页面。
- 子执行卡显示实际 Agent、模型、档位与运行状态；缺配置直接定位相应设置。
- Progress 展示目标相关工作、待核验项和真实等待原因；Capture 展示实际活动输入、设备及切换／恢复状态。
- Knowledge 页面承接分页、渐进读取和主题批量确认。
- 使用既有 Button、语义 token、焦点和状态规范，覆盖深浅主题、窄屏、键盘及错误状态，不另造视觉体系。

文档同步采用单一权威：

- 将收敛设计中仍保留的“General＋Skill＋用途模型配置”建议替换为本次已定方案。
- 将稳定内容融入现有产品、运行、权限、失败、RDC 和 UI 主题文档；修正“四个唯一官方身份”、旧 root 两轮预算、Scout／Skeptic 仅为 General 别名等冲突。
- `ARCHITECTURE.md` 保留架构裁决，`AGENTS.md`、`DESIGN.md` 仅同步受影响原则；任务进度和机器现场不写成永久规则。
- 清除被替代的执行入口、类型、提示词、测试和引用，不保留兼容别名或新旧双路径。

数据转换沿已授权的一次性方式实施：

- 先清点受影响配置和可恢复状态，生成备份及转换预览，校验后原子替换；正常运行只读取新合同。
- 历史冻结请求、签名证据和原始日志不重写。无法可信转换的旧执行保留为历史诊断，不伪造新 Profile 执行证明。
- 在途任务先安全停止；转换后从检查点重新准备，不自动重启。
- 不扩大处理无关的历史格式，不删除真实会话、凭据、原始 capture 或唯一证据。

## 3. 执行顺序与持续追踪

实施开始时建立一个总体 Goal：**完成本计划全部实现、文档、可获得的运行验收与清理；未验证范围如实记录。** 不自设 token 或费用预算。

使用一份持久任务清单，状态统一为 `待执行 / 执行中 / 待验证 / 通过 / 阻塞`；每项记录依赖、改动、验收证据和阻塞原因。

| 顺序 | 交付单元 | 通过条件 |
|---|---|---|
| T0 | 基线、需求映射、数据清单及转换边界 | 收敛文档全部要求都有实现和验收落点 |
| T1 | Agent、模型配置与执行约束 | 八个 Agent 可配置；同步／后台实际请求符合目标 Profile |
| T2 | Knowledge 服务与管理链路 | 两项已知错误修复，查询、读取、版本和确认流程闭合 |
| T3 | 目标持续执行与完成合同 | 早停可继续，取消和真实限制不被绕过 |
| T4 | 三 Mission 方法、委派和压缩 | 短输入能形成检查，委派／压缩不丢目标与反证 |
| T5 | 多 capture 与受控恢复 | 身份切换、Android 重开、重新准备和消费保留成立 |
| T6 | UI、文档及一次性数据转换 | 实际状态正确呈现，权威一致，转换可验证和回退 |
| T7 | 综合验收、必要修复与清理 | 适用门禁通过，运行证据归档，资源与临时产物收口 |

文档和局部测试随各单元同步，不拖到最后补写。代码完成只能进入“待验证”。

## 4. 验证与验收

### 确定性合同

覆盖行为不同的代表正负路径：

- 文本零命中、词序变化、Scope、分页、内容版本变化，以及共同支持不产生虚构冲突。
- 正确 Profile、错误 Profile、缺配置、非法档位、父模型覆盖尝试、在途配置变化、同步／后台一致性。
- 必需核验缺失、审查完成但 blocker 未解决、产物更新导致审查失效、记录修正不强制重跑实验。
- 提前终答、合法续跑、用户取消、显式限额、等待批准、重复无进展及重启后消费保留。
- 跨 capture ID 混用、旧 lease、未登记输入、错误设备、恢复失败和中断实验拼接。
- 配置转换成功、失败回滚、历史证据不变，以及不支持记录保留原件。

### 方法与真实模型

- 使用同症状不同机制、不同症状同机制、知识条件不适用、零命中、反证、合理停止及压缩后的材料 fixture。
- 新增 Agent 使用已选定的 GPT 配置，记录实际 RequestPlan 和输出来源；不以设置页面显示正确代替请求验证。
- 对现有真实案例做“短症状 Prompt／仅补方法的详细 Prompt”对照，固定模型、知识、权限和干净回放状态，区分工具故障与方法差异。
- 分别评价 Debug 的区分证据、Analysis 的目标覆盖、Optimize 的真实测量与质量条件。
- 结果分类为自主完成、经提示完成、合理未完成、错误结论、过早停止和无效长跑；同时记录请求、时间、token、可得费用及人工介入。
- 陌生 capture 和独立真值不足时明确保留泛化验收缺口，不用历史案例或合成材料冒充。

### UI、设备与工程门禁

- Browser QA 使用 disposable 入口，验证 Agent 设置、真实执行投影、知识管理、停止、恢复和 Capture 切换；Android 实际回放另取回执。
- 运行受影响单测、`typecheck`、`lint`，以及设计 token、renderer 分层、session projection、right rail、investigation、repository hygiene 等适用检查。
- 跨层收口执行 `test:coverage`、`check:coverage-ratchet`、`check:gates` 和 `build`；无发布配置变更不制作发行包。
- 只因新出现的直接失败扩大修复和复测，适用验证通过后停止扩查。

## 5. 交付、清理与默认约束

- 在当前分支实施，不创建或切换分支；本计划不包含提交、推送或发布。
