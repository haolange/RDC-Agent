# 垂直调查收敛计划

本文自足：按它执行不需要先读其他文档。读者是在本机替用户监工的执行方，下文称"监工"。

工程约束以仓库根目录的 `AGENTS.md` 为准。领域目标的权威是[RenderDoc Agent 完整设计书](<../product/RenderDoc Agent 完整设计书.md>)：遇到本计划没有覆盖的领域问题时读它，第 0 章是产品裁决，第 10 章是 Debugger 的完整设计，第 5、6、7 章是循环、记录的读取时机和证据规则。三者冲突时，执行步骤和通过条件以本计划为准。

## 1. 目标

用户给一句症状，产品里的 Agent 能在当前 capture 上自主把问题查到底。

监工的工作是让这件事在三个真实案例上依次成立。监工不替产品里的 Agent 做调查：它启动真实调查、观察停在哪里、修掉导致停下的那一个原因、再跑。

## 2. 里程碑

按顺序做，一次只做一个。前一个由用户确认通过后才开始下一个。

| 里程碑 | 案例 | 回放 | 短症状 | 知识条件 |
|---|---|---|---|---|
| M1 | 头发发白 | Android 远程回放（骁龙 865） | 角色头发发白 | 知识库保持原样 |
| M2 | 头发发黑 | Android 远程回放（骁龙 8 Gen 1） | 角色头发发黑 | 知识库保持原样 |
| M3 | 眼部白点 | PC 本机 | 角色眼睛泪腺有白点 | 调查会话使用不含该案例材料的知识库；原知识库不改动 |

M1 和 M2 只走 Android 远程回放，不在 PC 本机回放顶替。每次开始前核对设备在线、capture 能打开、回放画面与设备一致。设备或材料不可用时停下报告，不换案例、不换设备。"不可用"指设备离线、锁屏无法操作或 capture 文件缺失。系统 ADB 显示设备在线而产品连不上，是产品连接层的缺陷：重启 ADB 服务后经产品重试一次；仍失败就把它当作本轮的直接原因，按 3.3 复现并修。

用户另有一个从未使用过的案例，只在三个里程碑都完成后由用户自己测试。监工不接触它，也不为它预做准备。

### 2.1 一轮调查的固定条件

| 项 | 取值 |
|---|---|
| 应用 | 隔离的应用实例和独立的 userData，不使用用户的真实会话数据 |
| Agent 与方法 | 使用仓库内置的 Profile、Skill 和 Hook。隔离的用户资源目录里不放 `agents/`、`skills/`、`hooks/`、`policies/` 的任何覆盖，只带登录凭据和 RDC 工具配置。启动前在 Settings 的 Agents 页确认四个入口和八个内部 Agent 的来源都是内置 |
| 轮次上限 | 不设（内置 Profile 不声明 `max-turns`） |
| 会话 | 每轮新建，不复用上一轮的会话。旧的隔离会话在里程碑进行中一律保留，不删除；里程碑结束后由用户决定是否清理 |
| 模型 | ChatGPT Account / gpt-6.1-sol / Medium；Fast 与 Max 关闭 |
| 权限模式 | 自动审核（应用默认） |
| Memory | 关闭 |
| Knowledge | 按里程碑表 |
| 输入 | 只输入里程碑表里的短症状，不附加方法、提示或坐标 |

回放需要调整设备配置才能打开时（见第 6 节），由监工在启动调查前完成，并记入该轮记录；这不算对调查的介入。

### 2.2 监工在一轮中可以做的事

- 批准计划，不修改计划内容。
- 点击执行按钮。
- 批准产品弹出的权限确认。
- 回答产品主动提出的澄清问题：只使用本计划里程碑表中的事实（案例对象、设备）。问题超出这些事实时回答"不知道"，或选择跳过。

除此之外的输入都算介入：补充调查方法、指出区域或事件、催促继续、在 Agent 停下后要求它再试。发生介入的那一轮不能算通过。

### 2.3 一轮调查怎样算通过

同时满足以下五条。前四条由监工对照调查记录判断，第五条由用户判断。

**(1) 自主**：整轮没有 2.2 之外的介入。

**(2) 走完主线**：会话的调查记录里能逐项找到下表的依据。

| 步 | 要求 | 记录中的依据 |
|---|---|---|
| 锚定 | 证明某个原生纹理区域和 draw 就是用户所说的对象 | 一条 `observed` 的 Evidence，summary 以 `user-confirmed` 或 `cross-validated` 开头，引用了像素历史以及 draw 覆盖或 mesh、绑定资源的工具结果；一条 Claim 写明区域到 draw 的对应 |
| 首次异常 | 把异常的出现定位到一个事件区间，有读数为证 | 一条 Evidence，`region.kind` 为 `event` 或 `pixel`，带区间两端的读数（之前正常、之后异常）；一条 `observed_fact` Claim。区间由抽样或二分得到即可，不要求逐个排除区间之外的全部更早写入 |
| 区分 | 替代解释都得到处理 | `hypothesis` Claim 各自有裁决（接受、排除、降级或暂缓并写明理由）；针对它们的 Challenge 不是 `open` |
| 因果 | 结论有可恢复的对照实验支持 | 一条 Experiment，`executionEvidence` 五份回执齐全，状态为 `recorded` 或 `rolled_back`，rollback 已执行且基线已恢复；一条 `causal_conclusion` Claim 引用它并写明适用范围 |
| 核验 | 独立审查读过当前版本的原始证据 | verifier 的 Task 中有对被审记录及其证据的读取，读取时的 hash 等于记录当前的 contentHash；没有 `open` 的 Challenge；最终的完成声明被产品接受。过程中被拒绝后补齐再通过，属于正常流程 |

当前产品能力做不了所需干预时，"因果"一步可以是能力阻塞。成立条件有三：监工经产品路径确认了能力目录里没有可用的干预，且没有其他现有能力能达到同样效果；Agent 的未决项里写明了缺的是哪种干预；Agent 已经把不需要干预的证据做到头，即读出了候选机制在该 draw 上的实际状态，并给出了一项只有该机制成立才会出现的可观察特征及其读数。结论的验证等级如实标为差分支持，不标为因果。

**(3) 历史知识经过验证**：结论引用历史案例时，有当前 capture 上的读数或实验支持它。只复述历史案例的原因不算。

**(4) 现场恢复**：回放回到进入时的 capture 与位置，有恢复回执。

**(5) 用户确认结论正确**：监工把结论交给用户，用户对照自己掌握的真实原因判定。监工不知道真实原因，不去猜，也不去找。

Challenge 只记录阻止结论按现措辞成立的缺口；不影响结论成立的审查意见在审查结果里标 `not_required`，进交付的未知项，不算 open Challenge。

表中的"依据"用来确认每一步确实做了，不是比主线更高的门槛。因果一步成立（干预后恢复、撤销后重现）且核验通过时，前面三步按实质判断：记录能支撑结论就算满足，不因为记录的形式不够穷尽而判不满足。拿不准时照常交付，把疑点写明，由用户判断。

产品声明 `partial` 时，两种情况可以交付给用户：

- 因果一步已经成立（有五份回执齐全的可恢复实验，干预改变了结果、撤销后复原），剩下的只是"干预后的样子是不是正常"或范围是否完整。
- 因果一步是上面定义的能力阻塞，且三个条件都满足。

其余的 `partial` 或 `blocked` 是停点，按第 3 节继续循环。"需要扩大产品能力才能做干预"本身不触发 3.5 的停止：先把差分证据做到头并交付，是否扩能力由用户在看到结果后决定。

前四条都满足时，停下交付，等用户判第五条。

## 3. 工作循环

对当前里程碑重复以下四步。

### 3.1 跑

按 2.1 的条件新建会话，输入短症状，等 Mission 交出计划后批准并点击执行，直到 Agent 声明结果或停下。

### 3.2 看

对照 2.3 的表，从"锚定"起逐步检查，找到**第一个不满足的步**。这一步就是本轮的停点。

### 3.3 查

目的只有一个：确定停点的直接原因在哪一层。

1. 读 Agent 交付的未决项和最后几步的工具结果。
2. 未决项里列为"未执行"或"不可用"、且直接挡住停点的检查，监工经同一产品路径重放：每轮最多 3 项，每项一次。成功说明 Agent 没有选它；失败说明工具或环境有问题，保留错误原文。
   两个工具对同一对象给出不一致的结果、需要分清问题在 RDC-Tool 还是 RenderDoc 原生层时，监工可以在隔离环境里直接用 RenderDoc 的 Python API 做只读对照：每轮一次，不修改源码、二进制和 capture，结果记入账本。这不需要另行请示。
3. 需要看模型实际收到了什么时，读该会话 Trace 里的请求记录，不靠推测。
4. 判定直接原因属于哪一层：工具返回、方法文本、运行时，还是模型能力。

判定规则：

- 重放中工具返回错误、缺字段或降级的数据，是**工具返回**层，即使 Agent 没有走到那一步也先修它：它迟早挡路。
- Agent 手里有可用的检查却没有选，是**方法文本**层。查它实际读到的方法文本里，这一步是否写在它当时会看的位置、是否被更长的内容淹没、是否与别处矛盾。
- 预算或期限耗尽不是原因，是现象。数清预算花在了哪里（各类工具调用的次数、读方法文本和写记录各占多少），直接原因是花得最多又没有推进主线的那一类，归入方法文本或运行时。
- **模型能力**只在这种情况下成立：同一步已经做过三轮方法文本或工具层的修复，Agent 每次都读到了正确且无矛盾的指引、工具也都可用，仍然不选。第一轮不能下这个结论。

每轮都必须得出一个可以修的直接原因，或者落入 3.5 的情形。"没有证据支持确定的修复"不是结论：证据不够就按上面第 2、3 步取够。

不做更大范围的排查。

### 3.4 修

只修 3.3 判定的那一个直接原因，按第 4 节的规则提交，然后回到 3.1。

### 3.5 停止并报告

出现以下任一情形时停下，向用户报告：

- **原地不动**：连续三轮修复后，停点仍是主线的同一步，且直接原因仍在同一层。停点前移或直接原因换了层，计数清零。
- **轮数上限**：当前里程碑已跑满 12 轮。
- 直接原因是模型能力（按 3.3 的判定规则成立）。
- 修复需要新增存储、模型路由、Agent、固定流程或扩大权限，或需要用户才能做的决定。
- 设备、账号或材料不可用（按第 2 节的定义）。
- 回放在相同条件下重复崩溃或断连，**并且**当前这一步没有不经过该调用的取证路径。有替代路径时不停：那个调用不再重试，调查经替代路径继续；该故障另按下面"回放故障"处理。

报告写清：停在哪一步、每次修复改了什么和结果、监工对原因的判断和依据。

### 3.6 回放故障

同一调用在相同条件下第二次导致崩溃或断连时：

1. 不再发起第三次相同调用。
2. 取一次设备端的崩溃现场（`adb logcat` 中 RenderDoc 远程服务的崩溃栈或退出原因）和 RDC-Tool 端的错误原文，记入账本。
3. 用最小的变化各试一次，找出触发条件：换同一资源上的另一个事件、换同一事件上的另一个目标资源、换一个 mip 或 sample。每种变化一次。
4. 结论是工具或回放层缺陷且可以修时，它就是本轮要修的那一个原因。修不了时，在工具返回里把该条件标成不可用并给出原因，让调查能据此改走替代路径。

锚定这一步的替代路径：在候选事件之前和之后读取同一原生区域的数值来确定写入事件，再用 draw 覆盖高亮或事件前后差异确认对象归属。

### 3.7 里程碑通过后

用户确认通过后，开始下一个里程碑之前，把已通过的案例各重跑一次。某个已通过的案例不再满足 2.3 的前四条，就是回退：先解决回退，再继续。

## 4. 修复规则

1. **一次一个原因。** 途中发现的其他问题记一行（现象、位置），不修、不查、不加测试。
2. **修复与案例无关。** 能用不提这个案例的一句话说清它修的是什么。
3. **方法文本按撰写规则改。** 规则（只减不增、不写案例等）见 [`docs/product/scoped-runtime-resources.md`](../product/scoped-runtime-resources.md)。
4. **不给失败加防护。** 不新增只用来拦截或上报失败的规则、状态检查、门禁和报告。边界上的契约校验不在此限。
5. **每个行为一条测试。** 只为新增或改变的行为写。
6. **不给失败找替身。** 不用静默替代值；数据无法解释时在返回里明确标注。
7. **工具缺陷先复现再改。** 回放工具（RDC-Tool）的问题，先经产品路径复现并保留错误原文，再改；不改它的二进制产物。
8. **每次修复单独提交**到当前分支，说明它消除了哪一步的哪个障碍。不创建、不切换分支。提交前跑受影响的测试、`pnpm run typecheck`、`pnpm run lint`。**每轮结束推送一次**（修复、账本和状态表；RDC-Tool 的修复推到它自己的仓库），无论本轮是继续还是停下。
9. **里程碑交付前**跑一次完整门禁与构建：`pnpm run check:gates`、`pnpm run build`，基线 `RDC_SYSTEM_DEBT_BASE_REF` 和 `RDC_DIFF_BASE` 指向本里程碑开始时的提交。
10. 不绕过产品权限；不删除、不上传真实用户数据、凭据和原始 capture；每轮结束释放回放现场并停止自己启动的进程。

## 5. 记录

- 每轮真实调查在 `docs/product/acceptance-ledger.md` 追加一条，不超过 10 行：案例、停点、直接原因、监工的输入、回放配置的调整、耗时与 token。
- 里程碑交付在对话里给出，不另建文件，不超过一页：结论、五步各自的记录位置、本里程碑做过的修复清单、未处理的旁支问题清单。
- 第 8 节状态表随进度更新。

## 6. 已知的候选问题

这些有源码依据但未在真实运行中确认。**不预先修**；某轮调查确实撞上时，按工作循环处理。

- 像素历史在无类型格式（TYPELESS）的目标上把颜色返回为未知。
- 回放工具把结构体里的未知枚举值转换失败，使整次查询失败并触发回放隔离重开。
- 整帧计时在部分 Android 设备上不可用。

以下是此前真实运行中出现过的回放问题，原因均未查明：

- Android 回放在默认配置下打开 capture 时出现过原生崩溃。当时在设备上保存原配置后把 RenderDoc 的 `SingleThreadedCompilation` 设为 true，发白案例得以打开并呈现。这是可逆的规避手段：使用前保存原配置，结束后恢复，并记入该轮记录。
- Android 上对上游资源做 Pixel History 时出现过远程连接丢失，回放现场被隔离。
- 发黑案例在 Adreno 上出现过管线创建阶段的崩溃，以及首帧观察时远程连接丢失。

## 7. 不做的事

- 不增加续跑次数，不用外部"继续"或停止钩子催促模型。
- 不新增存储、模型路由、循环引擎或 Agent。
- 不为了通过某个案例降低通过条件，也不修改本文的通过条件。
- 不把工程检查通过当作调查通过。
- 不同时推进两个里程碑。
- 不请求放宽 2.1 的固定条件（模型、档位、输入）。这些是被测条件，不是可调参数。

## 9. 能力补全：DXIL 中间表示的编辑与替换

### 9.1 要解决的问题

区分和因果需要单项修改：保留原 shader 的全部逻辑，只改其中一处。SPIR-V 已经能这样做。DXIL 目前只读，唯一的替换方式是提供一整份 HLSL。capture 里没有源码时，PC 上没有任何单项干预手段。

本节在 RDC-Tool 里补上"DXIL 文本中间表示 → 修改 → 装回 → 替换"，做法与现有的 SPIR-V 路径逐项对应。它属于现有 shader 替换能力的补全：不新增操作，不新增效果类型，回执和恢复边界不变。

### 9.2 与 SPIR-V 路径的对应

| 环节 | SPIR-V（已有） | DXIL（新增） |
|---|---|---|
| 可编辑的反汇编目标 | `SPIR-V ASM` | `DXIL ASM` |
| 文本来源 | 用 `spirv-dis` 反汇编 shader 的原始字节 | 用 DirectX Shader Compiler 工具链反汇编 shader 的原始容器字节，得到 LLVM IR 文本 |
| 文本识别 | `_looks_like_raw_spirv_asm` | 新增对应判定：文本含 LLVM IR 的函数定义和 `dx.op` 调用，仅有注释或诊断不算 |
| 编辑计划 | `input_kind=text_ir`，可编辑、可构建、可替换 | 相同；`requires_toolchain` 列出实际用到的工具，`build_input_kind=binary_dxil` |
| 允许的输入 | `source_text`、`diff_text`、`ops` | `source_text`、`diff_text`；本期不提供结构化 `ops`，`allowed_ops` 为空 |
| 构建 | `spirv-as` 装成二进制 | 装回 DXIL 容器，再经校验器校验并签名 |
| 交给回放 | `BuildTargetShader`（SPIR-V 编码）后替换 | `BuildTargetShader`（DXIL 编码，输入为容器字节）后替换 |
| 工具来源 | 随安装捆绑，`RDC_TOOL_SPIRV_TOOLS_PATH` 可覆盖 | 随安装捆绑，新增 `RDC_TOOL_DXC_TOOLS_PATH` 可覆盖 |

### 9.3 对外契约

- `rd.shader.get_disassembly`：shader 编码为 DXIL 时，接受 `target="DXIL ASM"`（或 `source_encoding="dxilasm"`），返回 LLVM IR 文本及其 `edit_plan` 和文本哈希。原生目标 `DXBC/DXIL` 的行为不变，仍然只读。
- `rd.shader.get_source`：DXIL 无源码时，`fallback_args` 指向 `DXIL ASM`；`blocked_reason` 改为说明这条可编辑路径，不再写"不要把反汇编交给 edit_and_replace"。
- `rd.shader.edit_and_replace` 与 `rd.shader.compile`：接受 `dxilasm` 文本。沿用 `expected_source_hash`，修改必须绑定到刚读到的那份文本。
- `rd.export.shader_bundle`：`disassembly_target="DXIL ASM"` 时导出可装配的文本，manifest 如实标注。
- 旧式 DXBC 字节码（非 DXIL）保持只读，`edit_plan` 明确说明原因。
- 非 Windows 主机不捆绑该工具链；`edit_plan` 照常返回，构建时以 `host_tool_unavailable` 拒绝。

失败一律在替换之前返回，带 `effects_attempted=false`、`context_preserved=true`：

| 情形 | code | category | details 里必须有 |
|---|---|---|---|
| 工具链缺失 | `host_tool_unavailable` | capability | 缺哪个文件、在哪里找过 |
| 文本装配失败 | `shader_assembly_failed` | validation | 装配器的原始诊断，含行号 |
| 校验或签名失败 | `shader_validation_failed` | validation | 校验器的原始诊断 |
| 回放拒绝构建结果 | 沿用现有的构建失败 | 沿用 | 回放返回的消息 |

不写静默回退：装配或校验失败时不改用其他目标、不跳过校验、不提交未签名的容器。

### 9.4 需要先查证的事实

以下几点我没有在这个工具链上验证过。动手前对照 DirectX Shader Compiler 的官方文档和所选发行包的实际内容确认，结果记入账本：

1. 反汇编：用哪个命令或接口从容器得到可重新装配的 LLVM IR 文本；输出里的注释头是否会妨碍装配。
2. 装配：发行包里是否带装配用的可执行文件。不带时，经 `dxcompiler` 的装配接口实现，不另找第三方工具。
3. 完整性：装回的容器是否带齐回放创建管线所需的各个部分（签名、资源绑定信息等）。只含 IR 部分时，从原容器保留其余部分的做法是否成立。
4. 校验与签名：未签名的容器能否被回放的 D3D12 设备接受；校验器如何签名，是否依赖随发行包分发的校验库，该库的再分发许可是什么。
5. 回放：`BuildTargetShader` 以 DXIL 编码接收容器字节时的行为，以及替换后的 shader 是否沿用原 shader 的入口和签名。

任何一点走不通，停下把原文报给用户，不绕行。

### 9.5 实现顺序

每一步通过后再做下一步。前两步只在隔离环境里手工验证，不改 RDC-Tool。

1. **原样往返**：从眼部 capture 取出一个 DXIL 像素 shader 的容器，反汇编，不改动，装回并校验签名，替换，确认该 draw 的输出与基线逐像素一致，撤销。
2. **最小修改**：把文本里一个浮点常量改成另一个值，装回、替换，确认输出发生变化；撤销后回到基线。
3. **接入工具**：按 9.2 和 9.3 实现。新增的工具链解析放进现有的主机工具契约（`host_tools`、主机布局、运行清单的来源与许可记录、doctor 的状态报告），打包脚本按钉住的版本和哈希取得。不改动运行时拆分后的模块边界。

### 10.2 一次请求怎样组装

按 provider 建立缓存前缀的顺序（tools → instructions → input）列出各部分，以及它们在同一回合的相邻请求之间会不会变。行号对应本轮起点 `9abb7c3`。

| 部分 | 来源 | 回合内会变吗 |
|---|---|---|
| tools | `RuntimeToolAssembly.ts:642-734` 的装配顺序；已激活的 deferred 工具追加在末尾（`deferredTools.ts:79-108`） | `tool_search` 激活新工具时变（`ToolExecutorFactory.ts:396-400`）；只剩一次请求时发空工具表（`AgentLoop.ts:323`） |
| instructions：core 四份文本、文件工具路由、Agent 正文、项目指令、预载 Skill、Skill 目录、工具能力表 | `PromptPlanBuilder.ts:100-177`，回合开始时冻结 | 不变 |
| instructions：`runtime:facts`、`runtime:profile-limits`、`runtime:approved-execution-offer`、`runtime:request-plan`、`runtime:execution-limits` | `PromptPlanBuilder.ts:179-266`、`TurnPreparationService.ts:189` | 不变 |
| instructions：`runtime:identity` | `PromptPlanRuntimeIdentity.ts:8-17` | 获批的 capture 切换或现场恢复后变，之后保持 |
| instructions：`runtime:continuation` | `RuntimeContinuationGuard.next`（`RuntimeContinuation.ts`）给出指令，`AgentLoop.ts` 的 `runtimeContinuationInstruction` 追加在末尾 | 只出现在"终答被运行时义务退回"后的那一次请求 |
| instructions：`runtime:permission` | `RuntimePermissionContext.ts:9-20`，每次请求追加在末尾 | 用户切换权限挡位时变 |
| input：历史消息 | 会话 journal；工具返回只追加不改写（`AgentLoop.ts:358-362`） | 只在末尾追加；压缩时重写窗口（`RecoverableContextWindow.ts:53-100`），之后稳定 |
| input：临时尾消息 | 无进展提示、余量提醒（`AgentLoop.ts:298-310,380-386`），不落盘 | 只影响当次请求的末尾 |

一个回合内，instructions 与 tools 在上表列出的少数事件之外逐字节不变。跨回合时 PromptPlan 重建，tool-loop 内的 reasoning 项从 journal 丢弃（`SessionContextJournal.ts:104-106,237-246`），新回合的历史从上一回合第一条带工具调用的助手消息起与前一请求不同。

缓存键与亲和：ChatGPT 账号路由沿用 `openai-responses` 协议的 `cache.mode: unknown`（`profiles/openai-responses.json:35`，`surfaces/chatgpt-account.json` 未覆盖），`PromptCacheCompiler.ts:30-33` 因此关闭缓存，请求既不带 `prompt_cache_key`，也不带 `session-id` 请求头（`responsesShared.ts:340-351`、`OpenAIResponsesProvider.ts:130-140`）。Codex CLI 对同一后端在请求体带 `prompt_cache_key`、请求头带 `session-id`，源码注释写明 ChatGPT 从 `session-id` 请求头推导缓存亲和（`openai/codex` 的 `codex-rs/core/src/client.rs`、`codex-rs/codex-api/src/requests/headers.rs`）。[源码]

据此，命中约 25% 有两种可能的主因，交接单 A 用同一份统计区分：

- 相邻请求覆盖前一请求的比例普遍在九成以上、缓存读取却低：内容是稳定的，主因是缓存亲和缺失。
- 首个差异位置集中在 tools 或 instructions 的某一段：是回合内有内容在变，按差异位置修。
