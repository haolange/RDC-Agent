# 垂直调查收敛计划

本文自足：按它执行不需要先读其他文档。读者是在本机替用户监工的执行方，下文称"监工"。

工程约束以仓库根目录的 `AGENTS.md` 为准。领域目标的权威是[RenderDoc Agent 完整设计书](<../product/RenderDoc Agent 完整设计书.md>)：遇到本计划没有覆盖的领域问题时读它，第 0 章是产品裁决，第 10 章是 Debugger 的完整设计，第 5、6、7 章是循环、记录的读取时机和证据规则。三者冲突时，执行步骤和通过条件以本计划为准。

## 1. 目标

用户给一句症状，产品里的 Agent 能在当前 capture 上自主把问题查到底。

监工的工作是让这件事在三个真实案例上依次成立。监工不替产品里的 Agent 做调查：它启动真实调查、观察停在哪里、修掉导致停下的那一个原因、再跑。

## 2. 里程碑

按顺序做，一次只做一个。前一个由用户确认通过后才开始下一个。

| 里程碑 | 案例 | 回放 | 短症状 | 知识条件 |
|---|---|---|---|---|
| M1 | 头发发白 | Android 远程回放（骁龙 865） | 角色头发发白 | 知识库保持原样 |
| M2 | 头发发黑 | Android 远程回放（骁龙 8 Gen 1） | 角色头发发黑 | 知识库保持原样 |
| M3 | 眼部白点 | PC 本机 | 角色眼睛泪腺有白点 | 调查会话使用不含该案例材料的知识库；原知识库不改动 |

M1 和 M2 只走 Android 远程回放，不在 PC 本机回放顶替。每次开始前核对设备在线、capture 能打开、回放画面与设备一致。设备或材料不可用时停下报告，不换案例、不换设备。

用户另有一个从未使用过的案例，只在三个里程碑都完成后由用户自己测试。监工不接触它，也不为它预做准备。

### 2.1 一轮调查的固定条件

| 项 | 取值 |
|---|---|
| 应用 | 隔离的应用实例和独立的 userData，不使用用户的真实会话数据 |
| 会话 | 每轮新建，不复用上一轮的会话 |
| 模型 | ChatGPT Account / gpt-6-luna / Medium；Fast 与 Max 关闭 |
| 权限模式 | 自动审核（应用默认） |
| Memory | 关闭 |
| Knowledge | 按里程碑表 |
| 输入 | 只输入里程碑表里的短症状，不附加方法、提示或坐标 |

回放需要调整设备配置才能打开时（见第 6 节），由监工在启动调查前完成，并记入该轮记录；这不算对调查的介入。

### 2.2 监工在一轮中可以做的事

- 批准计划，不修改计划内容。
- 点击执行按钮。
- 批准产品弹出的权限确认。
- 回答产品主动提出的澄清问题：只使用本计划里程碑表中的事实（案例对象、设备）。问题超出这些事实时回答"不知道"，或选择跳过。

除此之外的输入都算介入：补充调查方法、指出区域或事件、催促继续、在 Agent 停下后要求它再试。发生介入的那一轮不能算通过。

### 2.3 一轮调查怎样算通过

同时满足以下五条。前四条由监工对照调查记录判断，第五条由用户判断。

**(1) 自主**：整轮没有 2.2 之外的介入。

**(2) 走完主线**：会话的调查记录里能逐项找到下表的依据。

| 步 | 要求 | 记录中的依据 |
|---|---|---|
| 锚定 | 证明某个原生纹理区域和 draw 就是用户所说的对象 | 一条 `observed` 的 Evidence，summary 以 `user-confirmed` 或 `cross-validated` 开头，引用了像素历史以及 draw 覆盖或 mesh、绑定资源的工具结果；一条 Claim 写明区域到 draw 的对应 |
| 首次异常 | 找到异常最早出现的事件，有读数为证 | 一条 Evidence，`region.kind` 为 `event` 或 `pixel`，带事件前后的读数；一条 `observed_fact` Claim |
| 区分 | 替代解释都得到处理 | `hypothesis` Claim 各自有裁决（接受、排除、降级或暂缓并写明理由）；针对它们的 Challenge 不是 `open` |
| 因果 | 结论有可恢复的对照实验支持 | 一条 Experiment，`executionEvidence` 五份回执齐全，状态为 `recorded` 或 `rolled_back`，rollback 已执行且基线已恢复；一条 `causal_conclusion` Claim 引用它并写明适用范围 |
| 核验 | 独立审查读过当前版本的原始证据 | verifier 的 Task 中有对被审记录及其证据的读取，读取时的 hash 等于记录当前的 contentHash；没有 `open` 的 Challenge；完成时没有被拒绝（没有 `MISSION_COMPLETION_DENIED`） |

回放设备确实不支持所需干预时，"因果"一步可以是能力阻塞：Agent 的未决项里写明了阻塞条件，并且监工经同一产品路径重放该干预，得到同样的失败（见 3.3）。

**(3) 历史知识经过验证**：结论引用历史案例时，有当前 capture 上的读数或实验支持它。只复述历史案例的原因不算。

**(4) 现场恢复**：回放回到进入时的 capture 与位置，有恢复回执。

**(5) 用户确认结论正确**：监工把结论交给用户，用户对照自己掌握的真实原因判定。监工不知道真实原因，不去猜，也不去找。

前四条都满足时，停下交付，等用户判第五条。

## 3. 工作循环

对当前里程碑重复以下四步。

### 3.1 跑

按 2.1 的条件新建会话，输入短症状，等 Mission 交出计划后批准并点击执行，直到 Agent 声明结果或停下。

### 3.2 看

对照 2.3 的表，从"锚定"起逐步检查，找到**第一个不满足的步**。这一步就是本轮的停点。

### 3.3 查

目的只有一个：确定停点的直接原因在哪一层。

1. 读 Agent 交付的未决项和最后几步的工具结果。
2. 未决项里列为"未执行"或"不可用"、且直接挡住停点的检查，监工经同一产品路径重放：每轮最多 3 项，每项一次。成功说明 Agent 没有选它；失败说明工具或环境有问题，保留错误原文。
3. 需要看模型实际收到了什么时，读该会话 Trace 里的请求记录，不靠推测。
4. 判定直接原因属于哪一层：工具返回、方法文本、运行时，还是模型能力。

判定规则：

- 重放中工具返回错误、缺字段或降级的数据，是**工具返回**层，即使 Agent 没有走到那一步也先修它：它迟早挡路。
- Agent 手里有可用的检查却没有选，是**方法文本**层。查它实际读到的方法文本里，这一步是否写在它当时会看的位置、是否被更长的内容淹没、是否与别处矛盾。
- 预算或期限耗尽不是原因，是现象。数清预算花在了哪里（各类工具调用的次数、读方法文本和写记录各占多少），直接原因是花得最多又没有推进主线的那一类，归入方法文本或运行时。
- **模型能力**只在这种情况下成立：同一步已经做过三轮方法文本或工具层的修复，Agent 每次都读到了正确且无矛盾的指引、工具也都可用，仍然不选。第一轮不能下这个结论。

每轮都必须得出一个可以修的直接原因，或者落入 3.5 的情形。"没有证据支持确定的修复"不是结论：证据不够就按上面第 2、3 步取够。

不做更大范围的排查。

### 3.4 修

只修 3.3 判定的那一个直接原因，按第 4 节的规则提交，然后回到 3.1。

### 3.5 停止并报告

出现以下任一情形时停下，向用户报告：

- **原地不动**：连续三轮修复后，停点仍是主线的同一步，且直接原因仍在同一层。停点前移或直接原因换了层，计数清零。
- **轮数上限**：当前里程碑已跑满 12 轮。
- 直接原因是模型能力（按 3.3 的判定规则成立）。
- 修复需要新增存储、模型路由、Agent、固定流程或扩大权限，或需要用户才能做的决定。
- 设备、账号或材料不可用。
- 回放在相同条件下重复崩溃或断连。

报告写清：停在哪一步、每次修复改了什么和结果、监工对原因的判断和依据。

### 3.6 里程碑通过后

用户确认通过后，开始下一个里程碑之前，把已通过的案例各重跑一次。某个已通过的案例不再满足 2.3 的前四条，就是回退：先解决回退，再继续。

## 4. 修复规则

1. **一次一个原因。** 途中发现的其他问题记一行（现象、位置），不修、不查、不加测试。
2. **修复与案例无关。** 能用不提这个案例的一句话说清它修的是什么。代码、方法文本和知识里不出现案例的对象、事件、资源编号或原因。
3. **方法文本只减不增。** 改动 `resources/agent-runtime` 下的方法文本时，该文件的净字节数不增加；要加一句，先删掉等量的旧内容。
4. **不给失败加防护。** 不新增只用来拦截或上报失败的规则、状态检查、门禁和报告。边界上的契约校验不在此限。
5. **每个行为一条测试。** 只为新增或改变的行为写。
6. **不给失败找替身。** 不用静默替代值；数据无法解释时在返回里明确标注。
7. **工具缺陷先复现再改。** 回放工具（RDC-Tool）的问题，先经产品路径复现并保留错误原文，再改；不改它的二进制产物。
8. **每次修复单独提交**到当前分支，说明它消除了哪一步的哪个障碍。不创建、不切换分支。提交前跑受影响的测试、`pnpm run typecheck`、`pnpm run lint`。
9. **里程碑交付前**跑一次完整门禁与构建：`pnpm run check:gates`、`pnpm run build`，基线 `RDC_SYSTEM_DEBT_BASE_REF` 和 `RDC_DIFF_BASE` 指向本里程碑开始时的提交。通过后推送当前分支。
10. 不绕过产品权限；不删除、不上传真实用户数据、凭据和原始 capture；每轮结束释放回放现场并停止自己启动的进程。

## 5. 记录

- 每轮真实调查在 `docs/product/acceptance-ledger.md` 追加一条，不超过 10 行：案例、停点、直接原因、监工的输入、回放配置的调整、耗时与 token。
- 里程碑交付在对话里给出，不另建文件，不超过一页：结论、五步各自的记录位置、本里程碑做过的修复清单、未处理的旁支问题清单。
- 第 8 节状态表随进度更新。

## 6. 已知的候选问题

这些有源码依据但未在真实运行中确认。**不预先修**；某轮调查确实撞上时，按工作循环处理。

- 像素历史在无类型格式（TYPELESS）的目标上把颜色返回为未知。
- 回放工具把结构体里的未知枚举值转换失败，使整次查询失败并触发回放隔离重开。
- 整帧计时在部分 Android 设备上不可用。

以下是此前真实运行中出现过的回放问题，原因均未查明：

- Android 回放在默认配置下打开 capture 时出现过原生崩溃。当时在设备上保存原配置后把 RenderDoc 的 `SingleThreadedCompilation` 设为 true，发白案例得以打开并呈现。这是可逆的规避手段：使用前保存原配置，结束后恢复，并记入该轮记录。
- Android 上对上游资源做 Pixel History 时出现过远程连接丢失，回放现场被隔离。
- 发黑案例在 Adreno 上出现过管线创建阶段的崩溃，以及首帧观察时远程连接丢失。

## 7. 不做的事

- 不增加续跑次数，不用外部"继续"或停止钩子催促模型。
- 不新增存储、模型路由、循环引擎或 Agent。
- 不为了通过某个案例降低通过条件，也不修改本文的通过条件。
- 不把工程检查通过当作调查通过。
- 不同时推进两个里程碑。
- 不请求放宽 2.1 的固定条件（模型、档位、输入）。这些是被测条件，不是可调参数。
