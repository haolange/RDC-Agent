# 垂直调查收敛计划

本文自足：按它执行不需要先读其他文档。读者是在本机替用户监工的执行方，下文称"监工"。

理想架构的权威是[RenderDoc Agent 完整设计书](<../product/RenderDoc Agent 完整设计书.md>)。它写于产品实现之前，描述目标而不描述现状；遇到本计划没有覆盖的问题时去读它的对应章节。它与当前产品不一致的地方见第 8 节，以第 8 节和 `ARCHITECTURE.md` 为准。执行约束以本计划为准。

若某一步必须新增存储、模型路由、Agent、固定流程或扩大权限，停下并报告，不自行决定。

## 1. 目标

用户给一句症状，产品里的 Agent 能在当前 capture 上自主把问题查到底。

监工的工作是让这件事在三个真实案例上依次成立。监工不替产品里的 Agent 做调查：它启动真实调查、观察停在哪里、修掉导致停下的那一个原因、再跑。

## 2. 里程碑

按顺序做，一次只做一个。前一个由用户确认通过后才开始下一个。

| 里程碑 | 案例 | 回放 | 短症状 | 知识条件 |
|---|---|---|---|---|
| M1 | 头发发白 | Android（骁龙 865） | 角色头发发白 | 知识库保持原样（含相关历史案例） |
| M2 | 头发发黑 | Android（骁龙 8 Gen 1） | 角色头发发黑 | 知识库保持原样（含相关历史案例） |
| M3 | 眼部白点 | PC 本机 | 角色眼睛泪腺有白点 | 知识库无相关材料 |

每次开始前重新核对设备在线、capture 能打开、回放画面与设备一致。设备或材料不可用时停下报告，不换案例、不换设备顶替。

用户另有一个从未使用过的案例，只在三个里程碑都完成后由用户自己测试。监工不接触它。

### 一轮调查怎样算通过

同时满足：

1. **自主**：整轮中人工只做了三件事：批准计划、告知设备事实、回答产品主动提出的澄清问题。监工没有补充调查方法，没有催促继续。
2. **走完主线**：产品的调查记录里能逐项找到证据。

   | 步 | 要求 |
   |---|---|
   | 锚定 | 证明某个原生纹理区域和 draw 就是用户所说的对象 |
   | 首次异常 | 找到异常最早出现的事件，有读数为证 |
   | 区分 | 替代解释都得到处理：被观察削弱、排除，或说明为何仍无法区分 |
   | 因果 | 结论有可恢复的对照实验支持：最小干预后结果恢复，撤销后回到基线，并写明适用范围。回放设备确实不支持所需干预时，这一步可以是经事后重放证实的能力阻塞 |
   | 核验 | 独立审查读过当前版本的原始证据，没有未处理的质疑 |

3. **历史知识经过验证**：结论引用历史案例时，必须有当前 capture 上的读数或实验支持它；只复述历史案例的原因不算。
4. **现场恢复**：回放回到进入时的 capture 与位置，有回执。
5. **用户确认结论正确**：监工把结论交给用户，用户对照自己掌握的真实原因判定。监工不知道真实原因，也不去猜。

前四条由监工判断，都满足后停下交付，等用户判第五条。

## 3. 工作循环

对当前里程碑重复以下循环：

1. **跑**。新建隔离会话，输入短症状，按产品正常流程批准计划并执行。使用固定的模型与推理档位、默认自动审核权限、不带 Memory。
2. **看**。调查结束后，对照上表确定它停在主线哪一步。
3. **查**。对 partial 里列为未执行的每项检查，监工经同一产品路径亲自执行一次：成功说明 Agent 没有选它，失败说明工具或环境有问题，保留错误原文。再对照实际请求，判断直接原因在哪一层：工具返回、方法文本、运行时，还是模型能力。
4. **修**。只修导致这次停下的那一个直接原因，然后回到第 1 步。

满足通过条件的前四条时，停下交付。

**停止并报告的情形**：

- 同一步连续三次修复后仍停在原处。
- 直接原因是模型能力，改产品无法解决。
- 修复需要越过架构边界，或需要用户才能做的决定。
- 设备、账号或材料不可用。

报告写清：停在哪一步、试过哪三种修复、各自的结果、监工对原因的判断和依据。

**里程碑通过后**：开始下一个之前，把已通过的案例各重跑一次。出现回退时先解决回退。

## 4. 修复规则

这些规则优先于"做得更周全"的直觉。

1. **一次一个原因。** 途中发现的其他问题记一行（现象、位置），不修、不查、不加测试。
2. **修复必须与案例无关。** 能用不提这个案例的一句话说清它修的是什么。代码、方法文本和知识里不得出现案例的对象、事件、资源编号或原因。
3. **方法文本只减不增。** 改动后净字节数不得增加；要加一句，先删掉等量的旧内容。
4. **不加规则、状态检查、门禁或报告。** 修的是让调查走下去的障碍，不是给失败加防护。
5. **每个行为一条测试。** 只为新增或改变的行为写。
6. **不给失败找替身。** 不用静默替代值；数据无法解释时在返回里明确标注。
7. **每次修复单独提交**，说明它消除了哪一步的哪个障碍。跑受影响的测试、类型检查和 lint。里程碑交付前跑一次完整门禁与构建。
8. 不绕过产品权限；不删除真实用户数据、凭据和原始 capture；每轮结束释放回放现场并停止自己启动的进程。

## 5. 记录

- 每轮真实调查在验收账本追加一条，不超过 10 行：案例、停在哪一步、直接原因、人工说过什么、耗时与 token。
- 里程碑交付不超过一页：结论、五步各自的证据位置、本里程碑做过的修复清单、未处理的旁支问题清单。
- 下方状态表随进度更新。不另建报告。

## 6. 已知的候选问题

这些有源码依据但未在真实运行中确认。**不要预先修**；某轮调查确实撞上时，按工作循环处理。

- 像素历史在无类型格式（TYPELESS）的目标上把颜色返回为未知。
- 回放工具把结构体里的未知枚举值转换失败，使整次查询失败并触发回放隔离重开。
- 整帧计时在部分 Android 设备上不可用。

## 7. 不做的事

- 不增加续跑次数，不用外部"继续"或停止钩子催促模型。
- 不新增存储、模型路由、循环引擎或 Agent。
- 不为了通过某个案例降低通过条件，也不修改本文的通过条件。
- 不把工程检查通过当作调查通过。

## 8. 设计书与当前产品的对应

设计书先于产品写成。下列各项以当前产品为准，不按设计书原文实现：

| 设计书 | 当前产品 |
|---|---|
| Planning Orchestrator 经 Agent Handoff 自动交给执行方；Big Loop 自动交回规划方 | 用户批准计划并点击执行后才进入 General；需要重规划时 General 就地交付缺口，由用户切回 Mission。没有自动交接 |
| 领域职责名称（Triage、Capture Report、pass_graph_pipeline、pixel_value_forensics、shader_ir、Skeptic 等） | 四个用户入口（General、Debugger、Analyzer、Optimizer）和八个内部 Agent（generator、verifier、knowledge-scout、report-writer、shader／pass／resource／pixel-analyst）。Skeptic 即 verifier；其余职责由 Skill 承载 |
| 完成状态 Complete／Partial／Inconclusive／Blocked／Replanned | completed／partial／blocked／cancelled／budget_paused。Inconclusive 表达为 partial，并逐项写明未能区分的解释 |
| 检索含 Semantic／Embedding 作为补充 | 不使用 Embedding。Markdown 原文为唯一来源，六条检索通道 |
| 模型未作规定 | 模型与推理档位归各 Agent 配置；子执行不继承父对话的选择 |
| Debug Workflow 的 Reproduction Qualification、Pass／Resource Localization、Pixel／Value Trace | 对应本计划主线的"锚定"：先证明 capture 里的某个对象就是用户所说的症状，再往下查 |

设计书的以下内容直接适用，是判断调查质量的依据：中心因果闭环（1.3）、系统级不变量（3.3）、Live 与 Offline Task 的划分（4.7）、Small／Big Loop 的适用情形（5.5、5.6）、证据与结论的类型和验证等级（第 7 章）、Root Cause 的七段结构（7.4）、实验的事务性（7.6）、Debugger 完整设计（第 10 章）。
